# 프로젝트 계획

K리그 규정 17개를 근거로 조문을 인용하며 답하는 RAG 챗봇을 단계별로 만든다.
각 단계는 완료 기준의 테스트가 모두 통과해야 끝난다. 표시: ✅ 완료 / 🔄 진행 중 / ⬜ 예정

## 전체 흐름

```
PDF → 텍스트 추출 → 조문 단위 청킹 → 검색 → LLM 답변 → Streamlit 화면 → 배포
```

## 0단계. 하네스와 데이터 ✅
- 내용: 프로젝트 뼈대, 보안 설정, 규정 PDF 17개 확보
- 완료 기준
  - `tests/test_harness.py`: `docs_private/`와 `.env`가 git에서 제외되고, 읽기 금지 규칙이 설정되어 있음
  - `tests/test_download.py`: 개정 메모·해시 기준의 건너뛰기 판단이 동작함

## 1단계. PDF 텍스트 추출 ✅
- 내용: `src/extract.py`로 pdfplumber를 써서 페이지별 텍스트를 뽑고 메타데이터를 붙인다.
- 산출물: `data/extracted/*.json` (원문 파생물이라 저장소에 올리지 않음)
- 처리할 것
  - 머리말·쪽번호·목차·표지 제거
  - 제어문자 처리 (17번은 공백이 NUL 문자로 추출되므로 지우지 않고 공백으로 바꿈)
  - `body_text`를 기준일로 정규화 (`YYYY-MM-DD` + 개정/기준/제정 구분)
  - 표는 구조를 살려 추출 (전체 191개, 15·16번에 81·82개). `scripts/check_pdfs.py`의 `TABLE_SETTINGS`를 사용
  - 15번 30쪽은 페이지 텍스트 대신 `docs_public/manual/`의 수동 요약을 넣음
- 완료 기준 (`tests/test_extract.py`)
  - 17개 문서 전부 추출되고 페이지 수가 원본과 일치
  - 추출 결과에 제어문자·깨진 문자가 0개
  - 17개 문서 모두 기준일이 파싱됨 (예: 15번은 `2026-01-16`, 등록일 `2024-03-27`이 아님)
  - 표 샘플 3개 이상에서 행·열 내용이 보존됨 (09번 29쪽의 점선 괘선 표 포함)
  - 15번 30쪽의 수동 요약이 검색 대상 텍스트에 포함됨

## 2단계. 조문 단위 청킹 ✅
- 내용: `src/chunk.py`로 조문 하나를 청크 하나로 만든다. 긴 조문은 항 단위로 나눈다.
- 비교 기준선: 고정 길이 청킹 (800자, 겹침 100자). 3단계에서 정답률을 비교한다.
- 산출물: `data/chunks/article.jsonl`, `fixed.jsonl`
- 처리할 것: 문서마다 조문 형식이 달라 패턴을 나눠야 한다.
  - `제1조. 명칭`, `제 1조. 명칭`, `제1조 목적` (대부분)
  - `1조 (Article 1): 용어 및 정의`, 하위 `4.1`, `7.1.2` (15번)
  - 목차의 `제1조. 프로계약 ·····`는 조문으로 잡지 않음
  - 본문 속 참조(`제3조에 따른`)는 제목으로 잡지 않음
  - 부칙에도 `제1조`가 있으므로 본문 조문과 구분 (`부칙 제1조`)
- 완료 기준 (`tests/test_chunk.py`)
  - 문서별 첫 조문과 마지막 조문이 원문과 일치
  - 지정한 조문 10개 이상의 번호·제목·본문이 정답과 일치
  - 모든 청크에 규정명, 조 번호, 페이지, 기준일이 있음
  - 목차에서 나온 청크가 0개
  - 본문 제1조와 부칙 제1조가 서로 다른 청크로 구분됨

## 3단계. 검색 ✅
- 내용: `src/search.py`로 키워드(BM25)와 임베딩을 결합해 검색한다.
- 임베딩: `intfloat/multilingual-e5-small` (MIT, ONNX Runtime으로 CPU 실행). 비교 결과는 `eval/search_results.md`
- 검색 방식: 조문 청킹 + 키워드와 임베딩의 순위 융합. 규정명과 조번호를 직접 물으면 해당 조문을 맨 앞에 둠
- 비교 질문: 질문에 규정명이 2개 이상이면 규정별로 순위를 매겨 번갈아 고름
- 완료 기준 (`tests/test_search.py`)
  - `eval/questions.csv` 평가 질문 31개 사용 (답이 있는 문항 29개 기준)
  - 상위 5개 안에 정답 조문이 있는 비율 80% 이상
  - 조 번호를 직접 물으면(`선수 규정 제2조`) 해당 조문이 1위

## 4단계. LLM 답변 ✅
- 내용: `src/answer.py`로 검색 결과만 근거로 답하고, 규정명·조 번호·기준일을 인용한다.
- 처리할 것: LLM을 교체할 수 있게 만든다 (외부 API 모드 / 로컬 LLM 모드).
- 외부 API: `.env`의 `LLM_PROVIDER`로 groq(기본값)와 openai 중 선택. 둘 다 OpenAI 호환 API이며 키, 모델 이름, base_url만 다르다 (`env.example` 참고)
- 결정 필요: 로컬 LLM 모델. 지금은 교체용 인터페이스만 있고 로컬 구현은 없다
- 인용 목록은 코드가 검색 결과의 메타데이터로 만들고, 유효한 근거 번호가 없는 답변은 내보내지 않는다
- 외부 API에는 `visibility`가 `public`인 청크만 보낸다. 표시가 없으면 차단한다
- 완료 기준 (`tests/test_answer.py`, LLM은 가짜 객체로 대체)
  - 답변에 인용이 포함되고, 인용한 조문이 검색 결과에 실제로 있음
  - 근거가 없는 질문에는 "규정에서 찾을 수 없음"으로 답함
  - 시행일이 오늘 이후인 규정을 인용하면 `시행 전 (YYYY-MM-DD 시행 예정)`을 표시함 (`src/enforcement.py`)
  - 비공개 문서가 섞인 요청을 외부 API 모드로 보내면 전송 전에 차단됨
  - 평가 질문 10개를 실제 LLM으로 돌려 사람이 답변을 확인
- 최종 판정: 맞음 7, 일부 누락 3 (Q07, Q30, Q31), 틀림 0. 일부 누락은 아래 알려진 한계에 기록 (`eval/answer_results_v4.md`, `eval/answer_results_v4_repeat.md`)

## 5단계. Streamlit 화면 ✅
- 내용: `src/app.py`로 질문 입력, 답변, 근거 조문, 기준일을 보여준다.
- 상단 고정 안내 문구, 예시 질문 3개(Q01, Q14, Q19), 시행 전 표시, 근거 조문은 첫 번째만 펼침
- 공개 데모 보호: 질문 500자 제한, 세션당 5초 간격 제한. 걸리면 안내 문구만 표시
- LLM이 찾을 수 없다고 답했지만 검색 결과가 있으면, 코드가 검색 상위 조항 3개를 "참고: 관련될 수 있는 조항 (질문의 답이 아닐 수 있습니다)"로 원문 펼쳐 보기와 함께 표시. LLM 문장은 넣지 않음 (`docs/DEVLOG.md` 2026-11-09)
- 속도: 화면이 처음 열릴 때 검색기를 미리 만들고 임베딩 첫 계산을 치름(서버 프로세스당 1회). 질문 중에는 "1/2 규정 검색", "2/2 답변 작성" 진행 단계 표시. Streamlit은 브라우저 접속 시 스크립트를 실행하므로 서버 시작 직후가 아니라 첫 화면 열림 때 준비됨
- 답변 아래에 인용한 조문의 원문을 펼쳐 볼 수 있게 한다. LLM이 예외나 조건을 빠뜨려도 사용자가 원문에서 확인할 수 있어야 한다 (알려진 한계의 Q07, Q30)
- 완료 기준 (`tests/test_app.py`, Streamlit `AppTest` 사용)
  - 질문을 넣으면 답변과 근거 조문이 표시됨
  - 답변 아래에서 인용한 조문의 원문을 펼쳐 볼 수 있음
  - 검색 결과가 없거나 LLM 오류가 나도 화면이 깨지지 않음

## 6단계. 배포 🔄
- 내용: 공개 문서만 사용하는 버전을 Streamlit Community Cloud에 공개 앱으로 배포한다. 저장소는 GitHub 새 공개 저장소
- 결정 (사용자, 2026-11-09)
  - LLM은 Groq, 키는 Streamlit Secrets. 앱이 Secrets 값을 환경변수가 비어 있을 때만 옮긴다
  - 커밋 작성자 이메일은 GitHub noreply로 히스토리 수정 (공개 전)
  - 15·16번이 개정되면 앱을 멈추지 않고 기준일을 시행일로 대신 쓰며 "시행일 재확인 필요" 표시
  - 추출에 실패한 규정만 빼고 실행, 화면에 "일부 규정을 불러오지 못했습니다(규정명)" 표시
  - 서버 전체 사용량 제한: 분당 10회, 하루 200회(한국 시간 자정 기준). 서버 재시작 시 다시 셈
  - 라이선스 MIT. 규정 원문과 그 인용·요약은 대상이 아님
  - 개발 문서(CLAUDE.md, .claude/settings.json, PLAN, PROGRESS, DEVLOG) 전부 공개. 특정 기관의 내부 자료로 읽히지 않게 "비공개 문서"로 표기
  - 화면 상단에 "한국프로축구연맹 공식 서비스가 아닌 개인 포트폴리오 프로젝트입니다. 답변은 공식 해석이 아닙니다."
- 첫 실행 준비 (`src/bootstrap.py`): 청크 파일이 없으면 PDF 다운로드 → 추출 → 청킹. 다운로드가 실패해도 받은 PDF로 계속, 하나도 없으면 화면에 안내와 다시 시도 버튼. 임베딩 모델과 벡터는 첫 화면 열림 때 만든다
- 저장소 생성, 히스토리 수정 후 push, Cloud 배포는 사용자가 직접 한다
- 완료 기준 (`tests/test_deploy.py`)
  - 저장소와 배포 대상 파일에 규정 PDF, `docs_private/`, `.env`, 비공개 문서 인덱스, API 키가 없음 (히스토리 전체 포함)
  - PDF가 없는 빈 환경에서 첫 실행 시 PDF 17개가 받아지고 인덱스가 만들어짐
  - 다운로드 실패 시 앱이 오류 안내를 표시함
  - 배포 주소에서 평가 질문 3개가 정상 응답 (수동 확인)

## 알려진 한계
- 규정명 없이 두 규정을 비교하는 질문은 나눠 검색할 수 없다. Q31이 해당하며 비교 문항 3개 중 2개만 정답이다. 답변에서는 구단 조직도 20명 근거가 검색되지 않아 LLM이 K3리그 특례의 12명으로 답한다 (일부 누락). 지시문으로는 고칠 수 없는 검색 문제다.
- LLM이 근거에 있는 예외를 빠뜨릴 수 있다. Q07은 군팀 예외가 4회 모두 빠졌다. 근거 조문은 전달되었고, 예외 규칙을 구체화해도 달라지지 않았다. 질문이 금액만 물어 답을 좁게 쓴다고 추정하지만 원인은 확인하지 못했다. 원문 펼쳐 보기(5단계)로 완화한다.
- 같은 지시문에서도 답변이 실행마다 달라진다. Q30은 특수구급차 1대 조건을 온전히 쓴 답변이 4회 중 1회뿐이고, 1회는 "1대"만 생략, 2회는 조건 누락이다. 그래서 일부 누락으로 집계한다.
- 지시문 말투가 답변에 섞일 수 있다. Q30 4차 답변의 `시행 전임을 밝혀야 합니다`는 규칙 9의 표현이 그대로 나온 것으로 보인다. 시행 전 표시는 코드가 따로 붙이므로 정보는 빠지지 않고 문장만 어색하다.
- 순위 융합은 한쪽 검색에만 잡히는 정답의 순위를 낮춘다. Q22는 키워드 1위, 융합 16위였다. 키워드 1위를 상위 5개에 보장해 해결했다. 임베딩 1위는 보장하지 않으므로 임베딩에만 잡히는 정답은 여전히 밀릴 수 있다.
- Q10(드론)은 모든 조합에서 틀린다. 희귀어 5문항은 키워드로 모두 맞아 희귀어 일반의 문제로는 확인되지 않았다.
- 시행일은 규정 단위다. 조항별 시행일(예: 15번 I.04의 2030년 1월 1일 필수)은 본문 문구로만 알 수 있다.
- 시행일 계산은 개정 메모의 날짜를 이사회 의결일로 본다. 시행 조항이 없는 6개 규정(01, 03, 10, 12, 14, 17번)은 기준일로 대체한다.
- 12번은 사이트 메모(`2024년 1월 15일 제정`)와 PDF 개정내역(`2021/10/08 제정`, `2024/01/15 개정`)이 다르다. 기준일은 2024-01-15로 같고, 제정/개정 구분만 어긋난다.
- 15번 30쪽의 절차 흐름도는 이미지라 텍스트로 뽑히지 않는다. `docs_public/manual/`의 수동 요약으로 대체하며, 규정이 개정되면 요약도 다시 확인해야 한다.
- 15번의 표 안의 표는 글자는 보존되지만 행·열 구조가 바깥 셀 안에 풀린다 (47, 70, 71, 72쪽 등). 예: 연도별 사무국 인원. 2단계에서 답변 품질에 문제가 되면 다시 본다.
- 규정이 개정되면 파일이 교체된다. PDF는 git에 없으므로 이전 판은 남지 않고, 개정 메모와 해시 변화만 `manifest.json` 이력에 남는다.

- 지시문으로 해석을 금지해도 지켜지지 않을 수 있다. 부분 안내 시도에서 Q32가 4회 중 1회 "따라서 … 해야 합니다"로 결론을 냈고, 지시문을 되돌린 뒤에도 3회 중 1회 일반 답변으로 결론을 냈다. 대응은 세 겹이다: 지시문에 "질문이 가정한 상황이 근거에 없으면 찾을 수 없음" 규칙, 일반 답변에 결론 표지어(`따라서`, `그러므로`)가 있으면 코드가 찾을 수 없음 + 참고 목록으로 낮춤, 참고 목록은 LLM 문장 없이 코드가 만듦. 남는 한계: "~이므로", "~때문에", "~해야 합니다"처럼 표지어 없이 내린 결론은 막지 못한다. 또 규정 원문을 인용하다 "따라서"가 들어간 정상 답변도 낮춰질 수 있다. 참고 목록은 검색 순위라 관계없는 조항이 섞일 수 있다 (Q20은 연금과 관계없는 연봉·가입금 조항).
- LLM이 "규정에서 찾을 수 없습니다"라고 쓰면서 인용 번호도 달면 일반 답변으로 나간다. Q32 6차 3회 중 1회가 해당하며, "다만, …" 뒤에 조항 내용을 붙였다. 이번에는 해석이 없었지만, 이 경로에서는 LLM 문장이 "근거 조문" 아래 그대로 보이고 표지어 없는 해석은 막지 못한다. 사용자 결정으로 고치지 않음.
