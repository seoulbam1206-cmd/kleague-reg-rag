# 프로젝트 계획

K리그 규정 17개를 근거로 조문을 인용하며 답하는 RAG 챗봇을 단계별로 만든다.
각 단계는 완료 기준의 테스트가 모두 통과해야 끝난다. 표시: ✅ 완료 / 🔄 진행 중 / ⬜ 예정

## 전체 흐름

```
PDF → 텍스트 추출 → 조문 단위 청킹 → 검색 → LLM 답변 → Streamlit 화면 → 배포
```

## 0단계. 하네스와 데이터 ✅
- 내용: 프로젝트 뼈대, 보안 설정, 규정 PDF 17개 확보
- 완료 기준
  - `tests/test_harness.py`: `docs_private/`와 `.env`가 git에서 제외되고, 읽기 금지 규칙이 설정되어 있음
  - `tests/test_download.py`: 개정 메모·해시 기준의 건너뛰기 판단이 동작함

## 1단계. PDF 텍스트 추출 ✅
- 내용: `src/extract.py`로 pdfplumber를 써서 페이지별 텍스트를 뽑고 메타데이터를 붙인다.
- 산출물: `data/extracted/*.json` (원문 파생물이라 저장소에 올리지 않음)
- 처리할 것
  - 머리말·쪽번호·목차·표지 제거
  - 제어문자 처리 (17번은 공백이 NUL 문자로 추출되므로 지우지 않고 공백으로 바꿈)
  - `body_text`를 기준일로 정규화 (`YYYY-MM-DD` + 개정/기준/제정 구분)
  - 표는 구조를 살려 추출 (전체 191개, 15·16번에 81·82개). `scripts/check_pdfs.py`의 `TABLE_SETTINGS`를 사용
  - 15번 30쪽은 페이지 텍스트 대신 `docs_public/manual/`의 수동 요약을 넣음
- 완료 기준 (`tests/test_extract.py`)
  - 17개 문서 전부 추출되고 페이지 수가 원본과 일치
  - 추출 결과에 제어문자·깨진 문자가 0개
  - 17개 문서 모두 기준일이 파싱됨 (예: 15번은 `2026-01-16`, 등록일 `2024-03-27`이 아님)
  - 표 샘플 3개 이상에서 행·열 내용이 보존됨 (09번 29쪽의 점선 괘선 표 포함)
  - 15번 30쪽의 수동 요약이 검색 대상 텍스트에 포함됨

## 2단계. 조문 단위 청킹 ✅
- 내용: `src/chunk.py`로 조문 하나를 청크 하나로 만든다. 긴 조문은 항 단위로 나눈다.
- 비교 기준선: 고정 길이 청킹 (800자, 겹침 100자). 3단계에서 정답률을 비교한다.
- 산출물: `data/chunks/article.jsonl`, `fixed.jsonl`
- 처리할 것: 문서마다 조문 형식이 달라 패턴을 나눠야 한다.
  - `제1조. 명칭`, `제 1조. 명칭`, `제1조 목적` (대부분)
  - `1조 (Article 1): 용어 및 정의`, 하위 `4.1`, `7.1.2` (15번)
  - 목차의 `제1조. 프로계약 ·····`는 조문으로 잡지 않음
  - 본문 속 참조(`제3조에 따른`)는 제목으로 잡지 않음
  - 부칙에도 `제1조`가 있으므로 본문 조문과 구분 (`부칙 제1조`)
- 완료 기준 (`tests/test_chunk.py`)
  - 문서별 첫 조문과 마지막 조문이 원문과 일치
  - 지정한 조문 10개 이상의 번호·제목·본문이 정답과 일치
  - 모든 청크에 규정명, 조 번호, 페이지, 기준일이 있음
  - 목차에서 나온 청크가 0개
  - 본문 제1조와 부칙 제1조가 서로 다른 청크로 구분됨

## 3단계. 검색 ✅
- 내용: `src/search.py`로 키워드(BM25)와 임베딩을 결합해 검색한다.
- 임베딩: `intfloat/multilingual-e5-small` (MIT, ONNX Runtime으로 CPU 실행). 비교 결과는 `eval/search_results.md`
- 검색 방식: 조문 청킹 + 키워드와 임베딩의 순위 융합. 규정명과 조번호를 직접 물으면 해당 조문을 맨 앞에 둠
- 완료 기준 (`tests/test_search.py`)
  - `eval/questions.csv` 평가 질문 21개 사용 (기본 20개 + 시행 전 확인 1개)
  - 상위 5개 안에 정답 조문이 있는 비율 80% 이상
  - 조 번호를 직접 물으면(`선수 규정 제2조`) 해당 조문이 1위
- 다음 할 일: 3단계 결과에서 틀린 유형을 보고 평가 질문 10개 추가

## 4단계. LLM 답변 ⬜
- 내용: `src/answer.py`로 검색 결과만 근거로 답하고, 규정명·조 번호·기준일을 인용한다.
- 처리할 것: LLM을 교체할 수 있게 만든다 (외부 API 모드 / 로컬 LLM 모드).
- 결정 필요: 외부 API 모델, 로컬 LLM 모델
- 완료 기준 (`tests/test_answer.py`, LLM은 가짜 객체로 대체)
  - 답변에 인용이 포함되고, 인용한 조문이 검색 결과에 실제로 있음
  - 근거가 없는 질문에는 "규정에서 찾을 수 없음"으로 답함
  - 시행일이 오늘 이후인 규정을 인용하면 `시행 전 (YYYY-MM-DD 시행 예정)`을 표시함 (`src/enforcement.py`)
  - 비공개 문서가 섞인 요청을 외부 API 모드로 보내면 전송 전에 차단됨
  - 평가 질문 10개를 실제 LLM으로 돌려 사람이 답변을 확인

## 5단계. Streamlit 화면 ⬜
- 내용: `src/app.py`로 질문 입력, 답변, 근거 조문, 기준일을 보여준다.
- 완료 기준 (`tests/test_app.py`, Streamlit `AppTest` 사용)
  - 질문을 넣으면 답변과 근거 조문이 표시됨
  - 검색 결과가 없거나 LLM 오류가 나도 화면이 깨지지 않음

## 6단계. 배포 ⬜
- 내용: 공개 문서만 사용하는 버전을 배포한다.
- 주의: 15·16번이 개정되면 `src/enforcement.py`가 시행일 재확인을 요구하며 오류를 낸다. 첫 실행 다운로드에서 앱이 멈추지 않도록 처리 방식을 정한다.
- 처리할 것
  - 규정 PDF는 저장소에 없으므로 앱 첫 실행 때 `scripts/download_regulations.py`로 받는다.
  - 받은 파일로 인덱스를 만들고, 다운로드가 실패하면 화면에 안내한다.
  - 서버가 재시작되면 파일이 사라지는 배포처라면 다시 받는 시간을 고려한다.
- 결정 필요: 배포처, 공개 범위
- 완료 기준 (`tests/test_deploy.py`)
  - 저장소와 배포 대상 파일에 규정 PDF, `docs_private/`, `.env`, 비공개 문서 인덱스가 없음
  - PDF가 없는 빈 환경에서 첫 실행 시 PDF 17개가 받아지고 인덱스가 만들어짐
  - 다운로드 실패 시 앱이 오류 안내를 표시함
  - 배포 주소에서 평가 질문 3개가 정상 응답 (수동 확인)

## 알려진 한계
- 긴 조문 속 희귀어는 키워드 검색에서 흔한 낱말에 밀릴 수 있다. Q10(드론)이 모든 조합에서 틀린다. 추가 문항으로 같은 유형을 측정한 뒤 형태소 분석 도입을 판단한다.
- 시행일은 규정 단위다. 조항별 시행일(예: 15번 I.04의 2030년 1월 1일 필수)은 본문 문구로만 알 수 있다.
- 시행일 계산은 개정 메모의 날짜를 이사회 의결일로 본다. 시행 조항이 없는 6개 규정(01, 03, 10, 12, 14, 17번)은 기준일로 대체한다.
- 12번은 사이트 메모(`2024년 1월 15일 제정`)와 PDF 개정내역(`2021/10/08 제정`, `2024/01/15 개정`)이 다르다. 기준일은 2024-01-15로 같고, 제정/개정 구분만 어긋난다.
- 15번 30쪽의 절차 흐름도는 이미지라 텍스트로 뽑히지 않는다. `docs_public/manual/`의 수동 요약으로 대체하며, 규정이 개정되면 요약도 다시 확인해야 한다.
- 15번의 표 안의 표는 글자는 보존되지만 행·열 구조가 바깥 셀 안에 풀린다 (47, 70, 71, 72쪽 등). 예: 연도별 사무국 인원. 2단계에서 답변 품질에 문제가 되면 다시 본다.
- 규정이 개정되면 파일이 교체된다. PDF는 git에 없으므로 이전 판은 남지 않고, 개정 메모와 해시 변화만 `manifest.json` 이력에 남는다.
