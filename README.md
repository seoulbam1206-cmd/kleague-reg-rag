# K리그 규정 질의응답(Q&A) 서비스

K리그 공개 규정 17개를 근거로, 조문을 인용하며 답하는 규정 질의응답(Q&A) 서비스입니다.

> **한국프로축구연맹 공식 서비스가 아닌 개인 포트폴리오 프로젝트입니다. 답변은 공식 해석이 아닙니다.**
> AI 답변은 틀릴 수 있으므로 반드시 인용된 조문 원문을 확인하세요.

- 데모: https://kleague-reg-rag-egmydbc5th9ihxubeem2kg.streamlit.app/ (처음 열 때 규정을 받아 준비하느라 몇 분 걸릴 수 있습니다)
- 스택: Python 3.12, pdfplumber, BM25 + multilingual-e5-small(ONNX Runtime), Groq API, Streamlit

## 무엇을 하나
- 질문을 넣으면 관련 조문을 검색해 그 조문만 근거로 답하고, `[1]`처럼 근거 번호를 붙입니다.
- 답변 아래에 인용한 조문의 규정명·조 번호·기준일과 원문을 펼쳐 볼 수 있습니다.
- 시행일이 아직 오지 않은 규정을 인용하면 `시행 전 (YYYY-MM-DD 시행 예정)`을 표시합니다.
- 근거에 답이 없으면 "규정에서 찾을 수 없습니다"라고 답하고, 관련될 수 있는 조항을 원문과 함께 참고로 보여줍니다.

## 평가로 설계를 바꾼 과정
이 프로젝트는 정답률 숫자보다 **왜 틀렸는지 확인하고, 그 결과로 설계를 바꾼 기록**에 무게를 둡니다.
전체 기록은 [`docs/DEVLOG.md`](docs/DEVLOG.md)에 있습니다.

### 1. 가설을 데이터로 정정했다: "희귀어 약점"
- **관찰:** 19문항 검색 평가에서 Q10(드론)만 모든 검색 조합에서 틀렸습니다. "긴 조문 속 희귀어는 키워드 검색에서 흔한 낱말에 밀린다"고 설명하고, 형태소 분석기를 개선안으로 적었습니다.
- **검증:** 문항 하나에 맞춰 고치지 않고, 같은 조건의 문항 5개를 데이터로 뽑아 추가했습니다(715개 청크 중 3개 이하에만 나오는 낱말, 900자 안팎의 긴 조문). 조건은 테스트로 고정했습니다.
- **결과:** 키워드 검색은 5문항을 모두 맞혔습니다. 가설은 틀렸고 형태소 분석기 도입안을 철회했습니다.
- **새로 찾은 약점:** 순위 융합(RRF)은 한쪽 검색에만 잡히는 정답을 밀어냅니다. Q22는 키워드 1위였지만 융합 후 16위였습니다. 키워드 1위를 상위 5개 안에 보장하도록 고쳤습니다.

### 2. 나빠진 줄 알았는데 표기 문제였다
- **관찰:** 답변 지시문을 보완한 뒤 2차 평가에서 맞음이 7개에서 5개로 줄었습니다. 4문항이 "찾을 수 없음"으로 바뀌었는데, 검색 결과에는 근거가 있었습니다.
- **원인:** 지시문을 더 고치기 전에 LLM 원문을 결과 파일에 남기도록 바꿨습니다. 원문은 `...정합니다【1】.`로 정답이었고, 코드가 `[1]`만 읽어 인용 없는 답변으로 버리고 있었습니다.
- **결정:** 인용 표기 변형을 통일하고, "근거를 확인하지 못함"과 "규정에 없음"을 다른 문구로 구분했습니다.
- **평가 규칙:** 같은 지시문에서도 답이 실행마다 달라지는 것을 확인했습니다. 그래서 평소에는 11문항을 1회 돌리고, 판정이 달라진 문항만 3회 더 돌려 판단합니다.

### 3. 지시문의 금지를 코드 구조로 옮겼다
- **관찰:** 규정에 직접 답이 없는 상황 질문(구급차 1대가 이송으로 빠지면?)에서, 지시문으로 "결론을 짓지 말라"고 금지했지만 4회 중 1회 "따라서 … 해야 합니다"라는 해석이 나왔습니다.
- **결정:** 반드시 지켜야 하는 성질은 LLM이 아니라 코드가 보장하도록 구조를 바꿨습니다.
  - LLM은 근거에 답이 없으면 "찾을 수 없음"만 답합니다.
  - 참고 조항 목록은 검색 결과의 메타데이터와 원문만으로 코드가 만듭니다. LLM 문장이 들어갈 길이 없습니다.
  - 일반 답변에 결론 표지어(`따라서`, `그러므로`)가 있으면 코드가 "찾을 수 없음 + 참고 목록"으로 낮춥니다.
- **남은 빈틈:** 표지어 없이 내린 결론("~이므로", "~해야 합니다")은 막지 못합니다. 어느 경로를 막았고 어느 경로가 열려 있는지는 [알려진 한계](#알려진-한계)에 적었습니다.

## 평가 결과
평가 질문은 [`eval/questions.csv`](eval/questions.csv)의 32문항입니다(답이 있는 문항 30개, 규정에 답이 없는 문항 2개).

### 검색 (답이 있는 30문항, 상위 5개 안에 정답 근거가 있으면 정답)
| 청킹 | 검색 | 상위5 정답률 | 1위 정답률 | MRR |
| --- | --- | --- | --- | --- |
| 조문 단위 | 키워드(BM25) | 90% | 70% | 0.79 |
| 조문 단위 | 임베딩 | 83% | 67% | 0.74 |
| **조문 단위** | **융합 (채택)** | **93%** | **73%** | **0.82** |
| 고정 길이 800자 | 융합 | 93% | 60% | 0.75 |

전체 표는 [`eval/search_results.md`](eval/search_results.md)에 있습니다.

### 답변 (사람이 정답 요지와 비교해 판정)
| 차수 | 문항 | 맞음 | 일부 누락 | 틀림·찾을 수 없음 | 바꾼 것 |
| --- | --- | --- | --- | --- | --- |
| 1차 | 10 | 7 | 2 | 1 | |
| 2차 | 10 | 5 | 1 | 4 | 지시문 보완 → 인용 표기 문제 발견 |
| 3차 | 10 | 6 | 3 | 1 | 인용 표기 통일 |
| 4차 | 10 | 7 | 3 | 0 | |

| 6차 | 11 | 8 | 3 | 0 | 참고 목록을 코드로, 결론 표지어 낮춤 |

- 모델은 Groq의 `openai/gpt-oss-120b`입니다.
- 일부 누락 3건(Q07, Q30, Q31)은 원인과 함께 [알려진 한계](#알려진-한계)에 적었습니다.
- 결과 파일은 [`eval/`](eval/)에 차수별로 남겼습니다.

## 구조와 설계 원칙
```
규정 PDF ─ 추출(src/extract.py) ─ 조문 청킹(src/chunk.py) ─ 검색(src/search.py) ─ 답변(src/answer.py) ─ 화면(src/app.py)
```
- **조문 단위 청킹:** 규정마다 조문 형식이 다릅니다(`제1조.`, `1조 (Article 1):`, `4.1` 등). 목차와 부칙을 본문 조문과 구분합니다.
- **하이브리드 검색:** BM25와 임베딩 순위를 RRF로 합칩니다. 규정명과 조 번호를 직접 물으면 그 조문을 1위에 둡니다. 두 규정을 비교하는 질문은 규정별로 따로 검색합니다.
- **인용은 코드가 만든다:** LLM은 근거 번호만 씁니다. 규정명·조 번호·기준일·원문은 코드가 검색 결과의 메타데이터로 붙입니다. 유효한 근거 번호가 없는 답변은 내보내지 않습니다.
- **날짜:** 기준일은 파일명의 등록일이 아니라 공식 사이트의 개정 메모에서 가져옵니다. 시행일 규칙은 [`docs_public/manual/enforcement.json`](docs_public/manual/enforcement.json)에 따로 둡니다.
- **LLM 교체 가능:** Groq와 OpenAI를 같은 인터페이스로 씁니다. 비공개 문서용 로컬 LLM은 교체 가능한 인터페이스만 설계했고 아직 구현하지 않았습니다.
- **대화형이 아닌 단일 질의응답:** 규정 질문은 서로 독립적이고, 이전 대화를 검색에 섞으면 근거가 흐려지기 때문에 질문 하나에 답변 하나로 설계했습니다.

## 알려진 한계
자세한 내용과 근거는 [`docs/PLAN.md`](docs/PLAN.md)의 "알려진 한계"에 있습니다.
- **예외 누락 (Q07):** 근거 조문이 전달되어도 LLM이 군팀 예외를 빠뜨립니다. 원인은 확인하지 못했고, 원문 펼쳐 보기로 완화합니다.
- **실행마다 다른 답 (Q30):** 특수구급차 1대 조건을 온전히 쓴 답변이 4회 중 1회입니다.
- **규정명 없는 비교 질문 (Q31):** 규정별로 나눠 검색할 수 없어 근거가 검색되지 않습니다.
- **표지어 없는 해석:** "따라서" 없이 내린 결론은 막지 못합니다. LLM이 "찾을 수 없습니다"라고 쓰면서 인용 번호도 달면 일반 답변으로 나가는 경로도 열려 있습니다.
- **참고 목록:** 검색 순위일 뿐이라 질문과 관계없는 조항이 섞일 수 있습니다. 그래서 제목에 "질문의 답이 아닐 수 있습니다"를 붙이고 모두 접어 둡니다.
- **표와 이미지:** 15번 규정 30쪽의 흐름도는 이미지라 [수동 요약](docs_public/manual/)으로 대신합니다. 표 안의 표는 행·열 구조가 풀립니다.
- **시행일:** 시행일은 규정 단위로만 계산합니다. 조항별 시행일은 본문 문구로만 알 수 있습니다.

## 개발 방식
코드는 Claude Code가 작성했습니다. 저는 다음을 맡았습니다.
- **요구사항 정의:** 단계마다 무엇을 만들지, 화면에 무엇을 보여줄지, 공개 데모에서 무엇을 막을지 정했습니다.
- **하네스 설계:** AI 도구가 따를 규칙, 접근 권한, 단계별 완료 기준이 되는 테스트, 평가 체계를 설계했습니다(아래 [하네스 구성](#하네스-구성)).
- **평가 질문지 정답 검증:** 평가 질문의 정답 요지를 규정 원문과 대조해 확인했습니다.
- **판정 기준 결정:** 답변을 맞음, 일부 누락, 틀림으로 판정하는 기준과 차수별 최종 판정을 정했습니다.
- **설계 방향 결정:** 고칠지, 되돌릴지, 한계로 남길지를 정했습니다.

결정 사례 ([`docs/DEVLOG.md`](docs/DEVLOG.md))
- **1회 비교로 결론 내지 않는 규칙:** 같은 지시문에서도 Q30의 조건 누락이 3회 중 포함 1회, 일부 생략 1회, 누락 1회로 갈렸습니다. 그래서 판정이 달라진 문항만 3회 더 돌려 판단하는 규칙을 정하고 [`CLAUDE.md`](CLAUDE.md)의 평가 규칙에 넣었습니다. ("답변 평가 4회에서 찾은 것" 3번)
- **Q32를 지시문 대신 코드 구조로:** 지시문으로 해석을 금지한 방식에서 4회 중 1회 해석이 나오자, 지시문은 되돌리고 참고 조항은 코드가 검색 결과로 보여주는 구조로 바꾸기로 했습니다. ("2026-11-09: 해석 금지를 지시문에서 코드 구조로 옮긴 과정")
- **고치지 않고 한계로 남긴 것:** LLM이 "찾을 수 없습니다"라고 쓰면서 인용 번호도 다는 경로는 고치지 않고 알려진 한계로만 기록했습니다. ([`docs/PLAN.md`](docs/PLAN.md) "알려진 한계")

## 하네스 구성
이 프로젝트는 Claude Code와 함께 만들었습니다. AI 도구가 지켜야 할 규칙, 단계별 완료 기준, 진행 기록을 파일로 두고, 규칙 위반은 테스트로 잡습니다. 아래 파일은 모두 공개합니다.

| 파일 | 역할 |
| --- | --- |
| [`CLAUDE.md`](CLAUDE.md) | Claude Code가 세션마다 읽는 작업 규칙. 보안(비공개 문서·비밀키·규정 PDF 취급), 테스트 기대값을 바꿀 때는 보고 후 승인, 날짜 해석 규칙, 평가 실행 규칙, 자주 쓰는 명령어 |
| [`.claude/settings.json`](.claude/settings.json) | 규칙을 말이 아니라 권한으로 강제. `docs_private/`와 `.env` 읽기를 도구 수준에서 거부 |
| [`docs/PLAN.md`](docs/PLAN.md) | 단계별 내용과 완료 기준(어떤 테스트가 통과해야 끝인지), 사용자 결정, 알려진 한계 |
| [`docs/PROGRESS.md`](docs/PROGRESS.md) | 세션마다 한 일과 다음 할 일. 맨 위 "사용자 확인 필요"에 항목이 남아 있으면 다음 단계로 넘어가지 않음 |
| [`docs/DEVLOG.md`](docs/DEVLOG.md) | 설계 판단과 근거. 가설, 검증 설계, 결과, 정정, 배운 점 순서로 기록 |
| [`tests/`](tests/) | 단계별 완료 기준. `test_harness.py`는 비공개 폴더·`.env` 제외와 읽기 금지 설정을, `test_deploy.py`는 히스토리 전체에 PDF·키·비공개 파일이 없는지를 검사 |
| [`eval/`](eval/) | 평가 질문과 차수별 결과. 결과를 덮어쓰지 않고 남겨 비교 |

운영 원칙
- **사람이 결정하고 기록이 남는다:** 단계 시작, 기대값 변경, 판정 확정, 커밋은 사용자가 승인합니다. 결정은 PLAN과 PROGRESS에 남깁니다.
- **기대값을 맞추려고 테스트를 바꾸지 않는다:** 기대값을 바꿀 때는 무엇을 왜 바꾸는지 먼저 보고합니다.
- **비밀은 접근 자체를 막는다:** `.env`는 AI 도구가 읽지 않고, LLM 키가 필요한 평가는 사용자가 직접 실행합니다.
- **비공개 문서는 외부 API로 보내지 않는다:** 외부 API 모드에서는 공개 표시가 있는 청크만 보내고, 그 외는 전송 전에 차단합니다(테스트로 확인). 비공개 문서용 로컬 LLM은 교체 가능한 인터페이스만 설계했고 아직 구현하지 않았습니다. 그래서 지금은 비공개 문서를 읽는 기능이 없고, 공개 데모도 공개 규정만 씁니다.

## 배포 구성
Streamlit Community Cloud에 공개 앱으로 배포합니다.
- **규정 PDF는 저장소에 없습니다.** 앱이 처음 열릴 때 공식 사이트에서 받아 추출·청킹합니다. 한 규정의 추출이 실패하면 그 규정만 빼고 화면에 알립니다.
- **임베딩 벡터는 미리 계산해 저장소에 넣었습니다** ([`index/`](index/), 2.1MB).
  - 파일에는 모델 이름, 청크 내용의 해시(sha256), 숫자 벡터만 있고 규정 원문은 없습니다.
  - 서버는 청크 해시가 같으면 이 벡터를 쓰고, 규정이 개정되어 바뀐 청크만 새로 계산합니다.
  - 벡터로 원문을 대략 복원할 수 있다는 연구가 있으나, 이 규정은 공식 사이트에 이미 공개된 자료입니다.
  - 효과(로컬 측정): 빈 환경 첫 실행이 약 4.5분에서 2.5분으로, 최대 메모리가 약 2.0GB에서 1.3GB로 줄었습니다.
- **사용량 제한:** 세션마다 질문 500자, 5초 간격. 서버 전체로 분당 10회, 하루 200회(한국 시간 자정 기준).
- **시행일 재확인:** 시행일을 직접 지정한 규정이 개정되면 앱을 멈추지 않고 "시행일 재확인 필요"를 표시합니다.
- **Secrets:** `LLM_PROVIDER`, `GROQ_API_KEY`, `GROQ_MODEL` (선택: `HF_TOKEN`)

## 로컬 실행
```
python -m venv .venv
.venv/Scripts/python -m pip install -r requirements.txt   # Windows 기준
copy env.example .env                                      # 키와 모델 이름 입력
.venv/Scripts/python scripts/download_regulations.py       # 규정 PDF 받기
.venv/Scripts/python src/extract.py                         # 추출
.venv/Scripts/python src/chunk.py                           # 청킹
.venv/Scripts/python -m streamlit run src/app.py            # 화면
.venv/Scripts/python -m pytest                              # 테스트
```
PDF가 없으면 화면이 처음 열릴 때 받기·추출·청킹을 자동으로 합니다. 다른 명령어는 [`CLAUDE.md`](CLAUDE.md)의 "자주 쓰는 명령어"에 있습니다.
